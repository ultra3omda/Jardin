# V1.8 — UI super_admin de provisioning d'école — Spec

**Date** : 2026-05-25
**Statut** : Draft (en attente validation user)
**Référence roadmap** : nouvelle vague, à insérer entre V1.7 et V2

---

## 1. Contexte et objectif

### 1.1 Pourquoi maintenant

L'user veut **voir le flow end-to-end** « créer une école → l'école est immédiatement utilisable sur web + mobile » avant d'investir dans les modules métier (Élèves, Notes, etc.).

État actuel post-V1.7-A2 :
- API Railway en prod, web Vercel en prod, mobile Vercel en prod — chaîne CORS OK
- `/auth/register` (V1.5 invite-only) permet de créer un tenant + admin atomiquement à partir d'un invite token
- `POST /admin/invite-tokens` (SUPER_ADMIN) émet des tokens — mais **aucune UI** : il faut curl ou Swagger pour s'en servir
- Aucune liste de tenants visible côté super_admin

### 1.2 Objectif V1.8

Livrer une **UI super_admin web** qui permet de :
1. Lister toutes les écoles existantes (tenants) avec leur statut
2. Créer une nouvelle école en un formulaire (nom, slug, email admin, locale, brand color optionnel)
3. Voir, après création, les URLs immédiatement utilisables :
   - **Web pre-auth** : `https://ecole-saas.vercel.app/t/<slug>/login`
   - **Mobile preview** : `https://klasso-mobile.vercel.app` (avec le code école `<slug>` à saisir)
   - **Email invite admin** : envoyé automatiquement via Resend
4. Gérer les invite tokens existants (lister, revoquer)

**Hors scope V1.8** :
- Builds natifs séparés par école (M1 confirmé en roadmap → V12 EAS)
- Self-service public (toutes créations restent SUPER_ADMIN)
- Modification post-création des champs `name`/`slug` (immutable une fois créé)
- Suppression d'école (soft-delete + archive, V11 hardening)
- Upload logo/favicon depuis ce flow (réutilise `/settings/branding` V1.6 — l'admin école le fait elle-même après son 1er login)

## 3. Architecture

### 3.1 Backend (NestJS)

**Nouveau endpoint** :

```
POST /api/admin/tenants
SUPER_ADMIN required
Body:
  {
    name: string,           // "École Saint Pierre"
    slug: string,           // "saint-pierre" (lowercase, kebab-case, validated)
    adminEmail: string,     // futur admin de l'école
    adminFirstName: string,
    adminLastName: string,
    locale?: 'fr' | 'en' | 'ar' | 'es',  // default 'fr'
    type?: TenantType,      // 'PRIMARY' | 'KINDERGARTEN' | 'SECONDARY' (Prisma enum)
    primaryColor?: string,  // hex #RRGGBB optionnel pour pré-brand
    sendInviteEmail?: boolean,  // default true
  }
Response 201:
  {
    tenant: { id, slug, name, locale, type, brand, createdAt },
    inviteToken: {
      id, url, expiresAt   // URL = /register?token=...
    },
    inviteEmailSent: boolean
  }
```

**Comportement** :
1. Valider unicité `slug` (case-insensitive)
2. Créer `Tenant` (avec brand initial si `primaryColor` fourni — merge sur DEFAULT_BRAND)
3. Émettre un `InviteToken` avec `invitedEmail = adminEmail` + `intendedRole = SCHOOL_ADMIN` + `expiresInDays = 14`
4. Envoyer email Resend (template `tenant-invite.tsx` — nouveau) avec le lien `/register?token=...` + slug pré-rempli si possible
5. Logger `auth.tenant.created` audit event avec `metadata: { slug, createdBy: super_admin_id }`

**Pourquoi 1 endpoint et pas 2 (create tenant + invite séparément)** :
- Garantit l'atomicité (transaction Prisma)
- UI simplifiée (1 formulaire = 1 appel)
- Si invite email fail (Resend down), le tenant existe quand même et le super_admin peut renvoyer via UI

**Endpoints à lister/exposer (déjà existants ou à ajouter)** :
- `GET /api/admin/tenants` (nouveau) → liste tenants avec count d'users + status
- `GET /api/admin/tenants/:id` (nouveau) → détail d'un tenant
- `POST /api/admin/tenants/:id/resend-invite` (nouveau) → renvoie un invite si le premier a expiré et que le tenant n'a pas encore d'admin connecté
- `POST /api/admin/invite-tokens` (existant V1.5) → garder pour cas d'usage avancés (inviter un parent/teacher dans un tenant existant)

**Validation slug** :
- Lowercase a-z, 0-9, hyphens (pattern `^[a-z0-9][a-z0-9-]{1,61}[a-z0-9]$`)
- Réserve : `www`, `app`, `api`, `admin`, `assets`, `docs`, `status`, `mail`, `support`, `dashboard` (déjà dans `RESERVED_SLUGS` V1.7-A)
- Max 63 chars (RFC 1035 — préparation V1.7-B subdomain)
- Unique case-insensitive

### 3.2 Frontend Web (Next.js)

**Nouvelles routes** (sous `apps/web/app/(app)/admin/`) :

```
/admin/tenants                 → liste des écoles
/admin/tenants/new             → formulaire création
/admin/tenants/[id]            → détail d'une école (membres, invite status, brand preview links)
/admin/invite-tokens           → liste de tous les invite tokens (cas d'usage avancé)
```

**Guard** : layout `admin/` redirect `/dashboard` si `user.role !== SUPER_ADMIN`.

**Composants à créer** :
- `TenantList` : tableau avec colonnes `name`, `slug`, `createdAt`, `users count`, `actions`
- `TenantCreateForm` : react-hook-form + zod, validation côté client
- `TenantDetailCard` : preview brand color + 2 boutons "Voir web (logged-out)" + "Voir mobile (preview)" + lien copier invite URL

**UX post-création** :

## 6. Risques

| # | Risque | Mitigation |
|---|--------|------------|
| R1 | Resend down → email pas envoyé → super_admin doit re-déclencher manuellement | Endpoint `/resend-invite` + bouton UI + log `email.tenant_invite.failed` Sentry |
| R2 | Slug collision sous course concurrente | Contrainte DB unique + try/catch P2002 → 409 |
| R3 | Super_admin crée une école avec un slug réservé (`www`, `admin`...) | Validation côté API (RESERVED_SLUGS set) + Zod regex côté web |
| R4 | L'admin invité oublie son email / spam → ne s'inscrit jamais | UI permet de renvoyer + voir status pending. V11+ : nudge automatique J+7 |
| R5 | Création tenant + invite NON atomique (Resend dans transaction) | Le tenant + invite sont créés en transaction Prisma. L'email Resend est envoyé APRÈS commit (best-effort) — si Resend fail, le tenant existe et le bouton "Renvoyer" est disponible |
