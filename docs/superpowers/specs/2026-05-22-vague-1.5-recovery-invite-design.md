# Vague 1.5 — Recovery, Invite-only, Production hardening (design spec)

> **Statut** : Draft pour validation utilisateur.
> **Date** : 2026-05-22
> **Auteur** : Claude Code
> **Prérequis** : Vague 1 livrée en prod (auth multi-tenant, web Next.js, API NestJS, Postgres Neon).
> **Effort estimé** : ~2.5 jours.
> **Next** : Plan détaillé dans `docs/superpowers/plans/2026-05-22-vague-1.5-recovery-invite.md`.

---

## 🎯 Objectif

Combler les manques fondamentaux qui empêchent un déploiement public en prod :
- **Recovery flow** : un user ne peut pas récupérer son mot de passe oublié → bloqué à vie
- **Email verification** : risque de spam de tenants jetables si registration ouverte
- **Invite-only** (Q4=B) : seul un super-admin peut créer un nouveau tenant
- **Profil utilisateur** : pas d'UI pour modifier son nom/email/mot de passe/langue
- **DB migrations propres** : actuellement le repo utilise `prisma db push` — tout changement de schéma en V2+ = data loss potentielle
- **Super-admin login** : actuellement bloqué (`SUPER_ADMIN_LOGIN_NOT_SUPPORTED`), or il faut le débloquer pour émettre des invites
- **Data export RGPD** : endpoint pour qu'un user récupère toutes ses données (obligation légale FR)
- **Cookie consent** : prépare l'arrivée de PostHog en V2 (obligation RGPD)
- **Sentry boot** : capturer les erreurs prod dès maintenant (avant que ça parte de travers)
- **i18n infra** : poser la fondation pour les 4 langues (CLAUDE.md), mais ship `fr` only

## 📋 Scope détaillé

### 1. DB migrations switch (prérequis bloquant — R1 dans risk register)

**Problème actuel** : `apps/api/prisma/` n'a pas de dossier `migrations/`. CI utilise `prisma db push --skip-generate --accept-data-loss`. Production = idem au premier deploy. **Tout changement de schéma en V2+ = bug ou perte de données**.

**Solution** :
- Générer la migration initiale depuis le schéma actuel : `prisma migrate dev --name init_vague1 --create-only`
- Commit `apps/api/prisma/migrations/0001_init_vague1/migration.sql`
- Update `.github/workflows/ci.yml` : remplacer les 2 occurrences de `prisma db push` par `prisma migrate deploy`
- Update Railway runtime : ajouter un script de pre-deploy ou commit que `npm start` lance `prisma migrate deploy && node dist/main` (via le `start` script ou un wrapper)
- Update doc : `apps/api/README.md` mentionne `migrate dev` au lieu de `db push` pour les setups locaux
- Tests : ajouter un test CI qui vérifie qu'il n'y a pas de drift entre `schema.prisma` et les migrations (`prisma migrate diff --from-schema-datamodel ... --exit-code`)

**Effort** : 3h.

### 2. Schema update (préparation des nouvelles entités)

Une seule migration `0002_vague_1_5`, contient :

#### 2.1 `User` : ajout colonnes

```prisma
model User {
  // ... champs existants
  emailVerifiedAt DateTime?  // null = non vérifié, date = vérifié
  passwordChangedAt DateTime?  // pour invalider les sessions actives si pwd change
}
```

#### 2.2 `RefreshToken.tenantId` : passer nullable

Pour permettre au super_admin de se connecter (Q4=B nécessite super_admin login pour émettre invites).

```prisma
model RefreshToken {
  tenantId String?  // était String NOT NULL
  // ...
  tenant Tenant?  @relation(...)  // était Tenant (non-nullable)
}
```

#### 2.3 Nouvelle entité `EmailVerificationToken`

```prisma
model EmailVerificationToken {
  id        String   @id           // cuid2
  userId    String
  tokenHash String   @unique       // SHA-256 du token envoyé par email
  expiresAt DateTime
  consumedAt DateTime?
  createdAt DateTime @default(now())

  user User @relation(fields: [userId], references: [id], onDelete: Cascade)

  @@index([userId])
  @@index([expiresAt])
  @@map("email_verification_tokens")
}
```

#### 2.4 Nouvelle entité `PasswordResetToken`

```prisma
model PasswordResetToken {
  id        String   @id           // cuid2
  userId    String
  tokenHash String   @unique       // SHA-256 du token envoyé par email
  expiresAt DateTime
  consumedAt DateTime?
  ip        String?                // pour audit
  userAgent String?
  createdAt DateTime @default(now())

  user User @relation(fields: [userId], references: [id], onDelete: Cascade)

  @@index([userId])
  @@index([expiresAt])
  @@map("password_reset_tokens")
}
```

#### 2.5 Nouvelle entité `InviteToken`

```prisma
model InviteToken {
  id            String   @id           // cuid2
  tokenHash     String   @unique       // SHA-256 du token transmis à l'invité
  invitedEmail  String?                // optionnel : email pre-fillé sur /register?token=...
  intendedRole  UserRole              // SCHOOL_ADMIN par défaut (créateur d'un nouveau tenant)
  createdById   String                // userId du super_admin émetteur
  expiresAt     DateTime
  consumedAt    DateTime?
  consumedByUserId String?              // userId créé lors de la consommation
  createdAt     DateTime @default(now())

  createdBy User @relation("InviteTokenCreator", fields: [createdById], references: [id], onDelete: Cascade)

  @@index([expiresAt])
  @@map("invite_tokens")
}
```

#### 2.6 Index supplémentaires sur audit_logs

Pour les queries fréquentes RGPD export :

```prisma
model AuditLog {
  // ...
  @@index([userId, createdAt])  // déjà existant
  @@index([action, createdAt])  // nouveau — pour filtrer "tous les login.success de 2026"
}
```

**Effort** : 1h pour le schéma + migration.

### 3. Super_admin login activation

**Problème** : actuellement `AuthService.login()` lance `BadRequestException SUPER_ADMIN_LOGIN_NOT_SUPPORTED` si `user.role === SUPER_ADMIN`.

**Solution** :
- Supprimer ce check dans `auth.service.ts`
- `issueTokensAndBuildResponse()` : si `user.tenantId === null`, créer le RefreshToken avec `tenantId: null` (nullable depuis 2.2)
- Le JWT payload `{ tenantId: null, role: 'SUPER_ADMIN' }` est déjà géré par le `TenantContextInterceptor` (qui passe `skipTenantFilter: true` pour SUPER_ADMIN)
- Tests E2E : login as super_admin (depuis seed) → accessToken valide → `/api/auth/me` retourne `{ user: {...}, tenant: null }`

**Effort** : 1h (3 commits : remove check, update token issuance, add tests).

### 4. Invite token API

**Endpoints** :

```
POST   /api/admin/invite-tokens          Création (SUPER_ADMIN only)
  Body: { invitedEmail?: string, intendedRole?: UserRole, expiresInDays?: number }
  Response: { id, token (plaintext, one-shot), invitedEmail, expiresAt, url }

GET    /api/admin/invite-tokens          Liste (SUPER_ADMIN only)
  Query: ?status=active|consumed|expired

DELETE /api/admin/invite-tokens/:id      Révocation (SUPER_ADMIN only)
```

**Modifications register flow** :
- `POST /api/auth/register` : ajouter `inviteToken: string` au DTO (mandatory)
- `AuthService.register()` : valider le token (existe, pas expiré, pas consommé) → consommer → créer tenant + admin → retourner tokens
- Si `inviteToken` invalide → 400 `INVALID_INVITE_TOKEN`
- Web : `/register?token=xxx` → token pre-fillé en hidden field. Si pas de token dans l'URL → page "Demander un accès" avec mailto.

**Effort** : 4h (controller + service + DTOs + guards `@Roles(SUPER_ADMIN)` + tests).

### 5. Email verification flow

**Endpoints** :

```
POST   /api/auth/email/verify            Avec token
  Body: { token: string }
  Response: { user } (avec emailVerifiedAt set)

POST   /api/auth/email/resend            Renvoyer l'email (auth required, JWT)
  Response: 204
```

**Comportement** :
- À la création d'un user (register ou invite), envoyer un email avec link `https://ecole-saas-weld.vercel.app/verify-email?token=xxx`
- Token expire après **48h**
- Login bloqué si `emailVerifiedAt === null` → retourne 403 `EMAIL_NOT_VERIFIED` + propose "Renvoyer l'email"
- Web : page `/verify-email` consomme le token au load, affiche "✓ Email vérifié, vous pouvez vous connecter"

**Implémentation** :
- Service `EmailVerificationService` qui mint les tokens et envoie via `ResendService`
- Service `ResendService` wrapper sur `resend` package npm
- Template email JSX via `@react-email/components` (HTML + plaintext fallback)

**Effort** : 5h (Resend setup + templates + endpoints + web pages + tests).

### 6. Password reset flow

**Endpoints** :

```
POST   /api/auth/password/forgot         Envoie l'email de reset (anonymous)
  Body: { email: string }
  Response: 204 (toujours — pas de leak "email existe/pas")

POST   /api/auth/password/reset          Reset avec token
  Body: { token: string, newPassword: string (min 12) }
  Response: 204
```

**Comportement** :
- `/forgot` : trouve l'user par email (multi-tenant ambigu = `findMany`, on envoie l'email à toutes les addresses correspondantes — ou alternative : demander aussi `tenantSlug` comme login). **Décision : pas de tenantSlug requis** → si email existe dans plusieurs tenants, on envoie un seul email avec des liens distincts pour chaque tenant.
- `/reset` : valide token (24h expiry, one-shot) → hash bcrypt nouveau password → update `User.passwordHash` + `passwordChangedAt` → invalider toutes les sessions actives (revoke tous les `RefreshToken` non-revoked du user)
- Web : pages `/forgot-password` (form email) et `/reset-password?token=xxx` (form nouveau pwd)

**Effort** : 5h.

### 7. Page profil utilisateur

**Web** : nouvelle route `/profile` (dans le layout `(app)`, protégée).

**UI** :
- Section "Informations personnelles" : firstName, lastName, locale (select fr/en/ar/es — désactivés sauf fr en V1.5)
- Section "Compte" : email (read-only en V1.5, change-email = post-V1.5), bouton "Changer le mot de passe" (ouvre un modal avec currentPassword + newPassword)
- Section "Sécurité" : liste des sessions actives (refresh_tokens non-revoked) avec IP + userAgent + dernière utilisation, bouton "Révoquer cette session" et "Révoquer toutes les autres sessions"
- Section "Données personnelles (RGPD)" : bouton "Exporter mes données" (déclenche email avec ZIP — voir #8), bouton "Supprimer mon compte" (irréversible, soft-delete sur User + cleanup BullMQ planifié post-V11)

**API endpoints** :

```
GET    /api/users/me                       (déjà existe = /api/auth/me)
PATCH  /api/users/me                       Body: { firstName?, lastName?, locale? }
POST   /api/users/me/password              Body: { currentPassword, newPassword }
GET    /api/users/me/sessions              Liste RefreshTokens non-revoked
DELETE /api/users/me/sessions/:id          Révoque une session
DELETE /api/users/me/sessions              Révoque toutes (sauf current)
POST   /api/users/me/export                Déclenche export RGPD (envoi email asynchrone)
DELETE /api/users/me                       Soft-delete user (deletedAt = now)
```

**Effort** : 6h (controller + service + web pages + tests).

### 8. Data export RGPD endpoint (D13)

**Endpoint** : `POST /api/users/me/export` (auth required).

**Comportement** :
- Crée un job (synchrone pour V1.5 — pas de BullMQ avant V9) qui :
  1. Collecte toutes les données du user : profile, refreshTokens (sans hash), auditLogs, tenant info (lecture seule)
  2. Sérialise en JSON
  3. Zip le tout (`archiver` Node)
  4. Upload sur R2 dans un bucket `exports/` avec key `<userId>-<timestamp>.zip`
  5. Signe une URL R2 valide 24h
  6. Envoie un email au user avec le link de download (via Resend)
- Synchrone V1.5 = bloque la requête HTTP ~2-10s pour les gros users. Acceptable pour MVP.
- V9+ : passer en async via BullMQ worker.

**Effort** : 3h (R2 SDK setup + service + endpoint + email template + tests).

### 9. Cookie consent banner

**Composant web** : `apps/web/components/CookieConsent.tsx` (client component).

**Comportement** :

## 🏗️ Architecture

### Diagramme flux invite + recovery

```
1. Super-admin login
   Web /login → super@admin → JWT (tenantId=null, role=SUPER_ADMIN)
                                  ↓
2. Super-admin crée invite
   POST /api/admin/invite-tokens → token + URL
                                  ↓
3. Super-admin envoie URL manuellement (email ou Slack)
                                  ↓
4. Invité ouvre URL
   Web /register?token=xxx
                                  ↓
5. Invité fill form + submit
   POST /api/auth/register { tenant, admin, inviteToken }
                                  ↓
6. API valide invite, crée tenant + admin (transaction)
                                  ↓
7. API envoie email de vérification (Resend)
                                  ↓
8. Invité click link email
   Web /verify-email?token=xxx → POST /api/auth/email/verify
                                  ↓
9. Email vérifié → login débloqué
```

## 🧪 Stratégie de tests

### Unit (Vitest)

- `AuthService.register()` : valide invite token, consomme, gère collision slug, gère email déjà pris
- `EmailVerificationService.mint()` : génère token, stocke hash, expire à 48h
- `EmailVerificationService.consume()` : valide token, marque consumedAt, set `User.emailVerifiedAt`
- `InviteTokensService.create()` : génère token, stocke hash, retourne plaintext une seule fois
- `R2Service.signedPutUrl()` : génère URL signée
- `ExportService.collectUserData()` : produit la structure JSON

### E2E (Vitest + supertest)

- **Invite flow** : super_admin login → POST /admin/invite-tokens → curl /register?token=xxx → register OK → tenant créé
- **Email verification** : register → email sent (mock Resend) → POST /verify-email avec token → User.emailVerifiedAt set → login OK
- **Password recovery** : POST /forgot → email sent → POST /reset avec token → password updated → toutes sessions révoquées
- **Profile** : login → PATCH /users/me → update fields → assert DB
- **RGPD export** : login → POST /users/me/export → response 202 + email mock contient link R2

### Playwright (web E2E)

- **Invite flow web** : super_admin login UI → page admin (à créer minimal) → copie URL → ouvre /register?token=xxx → fill form → arrive sur /dashboard
- **Password reset web** : click "Mot de passe oublié" → entre email → reçoit email (intercepté en CI) → click link → entre nouveau pwd → login avec nouveau pwd
- **Profile UX** : login → naviguer /profile → update firstName → save → vérifier persisté

### Multi-tenant isolation (CRITICAL — R10)

Ajouter au test existant `multi-tenant-isolation.e2e-spec.ts` :
- `EmailVerificationToken`, `PasswordResetToken`, `InviteToken` → isolation tenant scope (sauf invite qui est super_admin-scoped, pas tenant)
- Vérifier qu'un user du tenant A ne peut pas consommer un token email du tenant B

## ⚠️ Risques spécifiques à V1.5

| Risque | Probabilité | Mitigation |
|---|---|---|
| Resend domain non vérifié → emails en spam | Haute | Setup DKIM/SPF sur le domaine Resend par défaut (`onboarding@resend.dev`) pour V1.5. Custom domain en V11 quand on aura le domaine OVH. |
| Migration `init_vague1` ne reflète pas exactement l'état de la DB Neon prod | Haute | Run `prisma migrate diff --from-url $NEON_URL --to-schema-datamodel schema.prisma` avant la migration pour générer le diff exact. |
| Existing prod users (créés via seed) n'ont pas `emailVerifiedAt` → bloqués au prochain login | **Critique** | Migration `0002_vague_1_5` doit aussi inclure un `UPDATE users SET email_verified_at = created_at` pour marquer tous les users existants comme vérifiés (legacy grandfathering). |
| R2 bucket pas encore créé → export RGPD fail | Moyenne | Documenter le setup R2 dans le plan + add bucket creation au pre-deploy checklist. |
| Super-admin peut accidentellement révoquer toutes les invites | Faible | Endpoint DELETE retourne 204 sans confirmation côté API. Confirmation UI à mettre en V10. |

- **Resend** : créer compte (https://resend.com) → générer API key → ajouter `RESEND_API_KEY` sur Railway. Le sender = `noreply@resend.dev` pour V1.5 (custom domain en V11).
- **Sentry** : créer compte (https://sentry.io) → créer projet `ecole-saas-api` (Node) + projet `ecole-saas-web` (Next.js) → récupérer 2 DSN → ajouter `SENTRY_DSN` sur Railway et Vercel.
- **Cloudflare R2** : créer compte (https://dash.cloudflare.com/) → créer bucket `ecole-saas-exports` → générer API token avec `Object Read & Write` → ajouter `R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `R2_BUCKET_NAME` sur Railway.

**Coût estimé V1.5** : $0 (tous les services en free tier).
