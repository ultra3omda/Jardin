# ADR 0002 — V1.5 Recovery, Invite-only, RGPD, Observability

**Status:** Accepted
**Date:** 2026-05-22
**Wave:** 1.5
**Builds on:** [ADR 0001 — Auth strategy and multi-tenant isolation](./0001-auth-strategy.md)

## Context

V1 shipped public self-service registration, no email verification, no
password recovery, no RGPD-grade data export, no error reporting, and a
single hard-coded French UI. That was acceptable for the MVP launch but
not for onboarding real schools. V1.5 closes those gaps without
introducing breaking changes for the existing V1 production users
(grandfathering rules below).

The orchestrating user locked two product calls before this wave :
- **Q3 = C** — defer the custom OVH domain (`ecole-saas.com`) to V11.
  V1.5 stays on `*.vercel.app` for web and `*.up.railway.app` for the API.
- **Q4 = B** — registration becomes **invite-only**. Super-admins mint
  single-use tokens; public `/register` is closed.

CLAUDE.md non-negotiables that govern the wave : TypeScript strict,
70%+ coverage, bcrypt rounds ≥ 12, no secrets in source, no PII in logs,
multi-tenant isolation verified by automatic test, RGPD-ready endpoints.

## Decisions

### 1. Invite-only registration (Q4 = B)

`POST /api/auth/register` now requires an `inviteToken` (Length 20-256)
in the request body. Tokens are minted by SUPER_ADMIN via
`POST /api/admin/invite-tokens` and persisted **only as SHA-256 hashes** —
the plaintext is returned once on creation and never again.

**Validation pipeline** (`AuthService.register`) :
1. Slug uniqueness check.
2. `InviteTokensService.validate(plaintext, email)` — pre-tx, throws on
   UNKNOWN / EXPIRED / CONSUMED / EMAIL_MISMATCH with a clear `code`.
3. Role guard : invite's `intendedRole` must be `SCHOOL_ADMIN` —
   `INVITE_ROLE_NOT_SUPPORTED_FOR_REGISTER` otherwise. The other roles
   (TEACHER, PARENT, STAFF) will be supported via invite-to-existing-
   tenant flows in V2+, not via `/register` which creates a brand-new
   tenant.
4. Inside the existing `$transaction(tenant + user)` we add
   `tx.inviteToken.update({ consumedAt, consumedByUserId })` so the
   consume is rollback-safe with the rest.

**Tradeoff** : we lose the public self-service signup funnel, gain
control over who creates a tenant. Acceptable for V1.5's stage (manual
sales pipeline). V2+ may reintroduce a "request access" form that
emails a super-admin instead of self-creating.

### 2. Email verification mandatory + grandfathering

V1.5 adds `users.emailVerifiedAt` (nullable DateTime). `AuthService.login`
throws `ForbiddenException { code: 'EMAIL_NOT_VERIFIED' }` when it's null.

**Grandfathering** : the V1.5 migration
`20260522000000_vague_1_5_recovery_invite` includes a one-shot
`UPDATE users SET emailVerifiedAt = createdAt WHERE emailVerifiedAt IS
NULL` so existing V1 users keep working.

**Token mechanics** mirror the invite tokens : 48h TTL, SHA-256 hash,
single-use, idempotent `mintAndSend` (no spam if already verified). The
email is best-effort — `mintAndSend` audit-logs the delivery result but
never throws, so a Resend outage doesn't block register.

`POST /auth/email/verify` is `@Public()`. `POST /auth/email/resend` is
authenticated and refuses with `EMAIL_ALREADY_VERIFIED` (400) when the
account is already good.

### 3. Anti-enumeration on `/password/forgot`

`POST /api/auth/password/forgot` returns **204 unconditionally**, whether
the email matches an account or not. An attacker probing emails cannot
distinguish a hit from a miss.

When a match exists, we mint a 24h SHA-256-hashed token, persist it with
the requester's IP + user-agent for audit, and email a 1-click reset link.
For an email shared across multiple tenants (rare but possible — a
parent enrolled at two écoles), one email is sent per matched account,
each with its own scoped token.

`POST /api/auth/password/reset` validates the token, then atomically :
1. Marks the token consumed.
2. Updates `users.passwordHash` (bcrypt rounds 12) + `passwordChangedAt`.
3. **Revokes ALL active refresh tokens for the user** — every existing
   session must re-login. Mitigates account-takeover scenarios where an
   attacker had a valid session before the legitimate owner reset.

The 24h window balances UX (delayed inbox check) and risk (long-lived
tokens harvested from email accounts).

### 4. Cloudflare R2 for RGPD exports

`POST /api/users/me/export` builds an in-memory ZIP via `archiver` of
the user's complete data footprint (profile, tenant, sessions, audit
logs cap 1000, email-verification + password-reset token history,
invites issued for super-admins), uploads it to R2 under
`exports/<userId>/<iso>-<cuid>.zip`, generates a 24h pre-signed
download URL, and emails the link.

**Why R2** : S3-compatible API (`@aws-sdk/client-s3` + `s3-request-presigner`)
plus a generous free tier (10 GB storage + 1M class A ops / mo) that fits
V1.5's expected volume (sub-MB exports, maybe a few per week). Zero
egress fees, unlike S3 — important if a user re-downloads multiple
times. Bucket-scoped tokens via "Object Read & Write" Account API
tokens (not User tokens) so they survive the user leaving an
organization.

The `R2Service` boots in **disabled mode** with a WARN log when any of
`R2_ACCOUNT_ID / R2_ACCESS_KEY_ID / R2_SECRET_ACCESS_KEY` is missing.
Calls into a disabled service throw `ServiceUnavailableException
R2_NOT_CONFIGURED` (503), so local dev / CI without R2 still boots —
they just can't exercise the export endpoint.

### 5. Sentry observability — free tier, 10% sampling, no Session Replay

Two projects on Sentry (`ecole-saas-api` Node.js + `ecole-saas-web`
Next.js) on the free tier (5k errors + 10k perf events / month).

**Tuning** in `instrument.ts` (API) + `sentry.client.config.ts` (web) :
- `tracesSampleRate: 0.1` in production, `0` elsewhere. 10% is enough
  to spot anomalies in p95 latency without burning the perf-events quota.
- `replaysSessionSampleRate: 0` + `replaysOnErrorSampleRate: 0`. Session
  Replay is a separate billing line and a PII risk surface — defer to
  V2+ when we have GDPR-compliant masking rules in place.
- `sendDefaultPii: false`. Sentry's default would forward request body
  / cookies / auth headers. We refuse — RGPD requires explicit minimisation.

**Sourcemap upload** is gated on `SENTRY_AUTH_TOKEN` being present in
Vercel/Railway env. When missing, the build still succeeds (the Sentry
webpack plugin warns then no-ops) — sourcemaps are quality-of-life,
not correctness.

**API integration** : `import './instrument';` is the very first line
of `main.ts` so Sentry can patch the HTTP/Express stack before any Nest
code loads. `SentryModule.forRoot()` is the first import in `AppModule`
and `SentryGlobalFilter` is the first `APP_FILTER` provider — both
ordering requirements per @sentry/nestjs docs.

### 6. i18n single-locale FR for V1.5

`next-intl` is wired (`i18n/request.ts`, `messages/fr.json`,
`<NextIntlClientProvider>` in the root layout, `withNextIntl` composed
with `withSentryConfig` in `next.config.mjs`) but the locale is
hard-pinned to `fr`. The catalog is a 10-key minimum-viable file —
existing pages still use inline French strings.

**Why infra-only for V1.5** : extracting every string from auth + profile +
admin pages is a multi-day effort with low V1.5 value (the product
launches in France first). With the wiring in place, the V2 i18n rollout
becomes a series of small per-page extraction PRs, not a foundational
rewrite. The `SUPPORTED_LOCALES = ['fr', 'en', 'ar', 'es']` constant in
`i18n/request.ts` documents the target set per CLAUDE.md.

V2 will add the `[locale]` route segment, the locale-switcher UI, and
the `useTranslations()` calls in components. Today's hooks
(`useTranslations()`, `getTranslations()`) already work for ad-hoc usage.

### 7. Full session revocation on password change

Both `POST /api/auth/password/reset` (forgot flow) and
`POST /api/users/me/password` (logged-in change) revoke **every** active
`RefreshToken` for the user, including the one currently in use.

**Tradeoff vs UX** : the user must re-login on the device they just
changed the password from. Mildly annoying but the right default :
- Attack scenario : an attacker who guessed/phished the password
  immediately sets a new one to lock the legitimate owner out. Without
  full revocation, the attacker's pre-change session stays alive after
  the legit owner resets.
- Recovery scenario : a legit user changed their password because they
  *suspected* compromise. They want every other session killed, full stop.

Per-session selective revocation lives in `DELETE /api/users/me/sessions/:id`
for non-emergency cleanup.

### 8. Cookie consent — informational only

V1.5 sets exactly one cookie (the httpOnly refresh-token cookie used to
restore sessions across reloads) and no third-party trackers. Under
ePrivacy/RGPD, **strictly necessary cookies are exempt from explicit
consent**. We still render an informational banner (`CookieConsent.tsx`,
persisted via `localStorage`) for two reasons :

1. Plain user transparency — surfacing the cookie's purpose is honest UX.
2. V2+ preparation — when we add analytics (probably PostHog or
   Plausible-self-hosted, RGPD-friendly), the banner becomes a real
   consent gate without UI rewiring.

The banner copy is explicit : *"École SaaS n'utilise qu'un cookie
strictement nécessaire à votre session d'authentification. Aucun cookie
publicitaire ou analytique n'est posé."*

### 9. Audit-log retention 2 years

`audit_logs` now has the composite `(action, createdAt)` index introduced
by the V1.5 migration. The retention policy is documented (CLAUDE.md +
this ADR) as **2 years** — long enough for RGPD's audit obligations,
short enough to bound the table growth. A scheduled pruning job
(`prune-audit-logs`) is V2 territory; for V1.5 the table is empty enough
that growth is not an issue.

## Consequences

### Schema migration risk (R1 from the V1.5 plan)

The switch from `prisma db push` (V1) to versioned `prisma migrate`
(V1.5) was the highest-risk change of the wave. We mitigated by :
1. Generating a baseline `0_init` migration matching V1 production
   schema exactly (verified by `prisma migrate diff`).
2. Marking it as already-applied on Neon prod via
   `prisma migrate resolve --applied 0_init` (no DDL executed).
3. Generating the V1.5 delta as a separate migration on top.
4. Refusing the "wipe schema" prompt that `prisma migrate dev` defaulted
   to under drift detection.

Future schema changes follow standard `prisma migrate` workflow —
no more `db push`.

### Test coverage

Each new flow ships with an e2e test that overrides `ResendService` via
`Test.createTestingModule().overrideProvider(ResendService).useValue(noop)`
so CI never consumes the Resend quota. The mock captures the rendered
JSX template props, which lets us extract verify/reset URLs from the
email body and exercise the full flow without a real inbox.

Critical paths covered by e2e :
- `auth.e2e-spec.ts` — register → email-verify → login → me → refresh → logout
- `invite-flow.e2e-spec.ts` — full invite mint/consume + 5 rejection codes
- `email-verification.e2e-spec.ts` — 9 tests incl. resend
- `password-recovery.e2e-spec.ts` — 7 tests incl. anti-enum + session revocation
- `profile.e2e-spec.ts` — 10 tests incl. cross-user session-revoke guard
- `multi-tenant-isolation.e2e-spec.ts` (V1, still required) — confirms the
  new V1.5 tables don't break the isolation contract

### Open follow-ups (V1.6+)

- `SENTRY_AUTH_TOKEN` setup for sourcemap uploads — already provisioned
  in Vercel env post-D6; will be picked up on the next build cycle.
- `global-error.tsx` for App Router-level error capture (Sentry warns
  about its absence today).
- Migrate Sentry's deprecated `disableLogger` to
  `webpack.treeshake.removeDebugLogging` per the v10 deprecation notice.
- `sentry.client.config.ts` → `instrumentation-client.ts` rename for
  Turbopack readiness.
- V2 i18n extraction — pages → `useTranslations()` per the design system.
- Custom domain (Q3=C deferred) — V11 hardening wave.
